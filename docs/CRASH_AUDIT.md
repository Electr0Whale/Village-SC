# 实机报错隐患审查报告

**现象**：游戏加载画面能出现，随后提示程序发生错误。
**结论**：报错的根源**基本可以确定是上一轮新增的 `romfs/data/fairy_1_00.dat`**（UI 贴图重打包）。数据库、字库和贴图路由之前已在实机测过（小地图汉化当时已经生效），本轮审查也没发现会导致崩溃的问题。

> [!CAUTION]
> 上一轮报告里写的“100% 位完全验证”是**循环验证**：读回检查用的是和写入时同一套（错误的）规则，所以测不出问题。这是我的失误。下面的结论都是重新拿 **Switch 原版文件**作为基准核对得出的。

---

## 一、致命问题：`fairy_1_00.dat`（必定导致崩溃）

审查脚本：`workspace/audit_fairy.py`、`audit_fairy_formats.py`、`audit_fairy_fmt_list.py`

### P0-1 压缩长度少算了 20 字节（66/66 张全部有问题）
| 字段 | Switch 原版规则 | 我写入的值 |
| :--- | :--- | :--- |
| `YKCMP_V1` 头里的 comp_sz | **20 字节头 + LZ4 数据**的总长 | 只算了 LZ4 数据 |
| `NMPLTEX1` 的 ints[12] | 同上（等于 YK comp_sz） | 只算了 LZ4 数据 |
| 描述符里的 nmpl_sz | 128 + ints[12] | 128 + 20 + LZ4（和 ints[12] 对不上） |

已验证：按原版规则（`LZ4_decompress_safe(src+20, comp_sz-20)`）解压，原版贴图都能成功，**我替换的 66 张全部失败**。引擎加载标题界面用的 `resident_lang_tc.fad` 时会直接解压出错，正好对应“加载画面之后报错”。

### P0-2 61/66 张贴图的像素格式不对
- Switch 版 411 张贴图里，描述符的格式字节分两种：
  - `0x07`：标准 BC3，解压后大小 = w×h（26 张）
  - `0x0B`：**另一种压缩格式**（385 张），解压后大小只有 BC3 的 0.56–0.75 倍，也不是 BC3。具体是 ASTC 还是带 mip 的 BC1/BC7，**目前还没确定**。
- 我把 PC 版的 BC3 数据塞进了格式字节仍是 `0x0B` 的 61 张贴图里，宽、高、格式字段都没改。引擎会按错误的格式、错误的大小去分配和上传，结果可能是 GPU 访问越界或断言失败。
- 66 张里只有 5 张原本就是 BC3（`0x07`）：#153–#156（传单 101–104）、#209（标题艺术字 Logo）。用户最关心的 #13（开始/设定）、#29（售价/种子、幼苗/收成天数）、#37/#55（分类）**全部属于 `0x0B`**。

### P0-3 Swizzle 块高用错了
- `NMPLTEX1` ints[14] 的低字节就是 Tegra 的块高 log2（取值 0–4），每张贴图不一样。
- 我所有贴图都固定用了 `mode=0`。实测 #209 正确的值是 `mode=3`（和原版 TC 比对，匹配率 100%）。就算修好前两个问题，画面也会是花的。
- 之前那个“swizzle 往返一致”的测试只能说明“先 swizzle 再反 swizzle 能还原”，证明不了 mode 选对了。

### P1 其它隐患
- `resident_lang_tc.fad` 从 124.1 MB 变成 136.8 MB（+13 MB），而这是常驻内存的资源。把 `0x0B` 换成 BC3 后显存/内存占用会变大，Switch 上有可能因为内存池不够而崩溃。
- 没有替换的 8 张（3 张告示牌、2 张演出图 2200×1300、`shoppingline01` 256×16、`bg_8080` 两张尺寸不一致）仍然是繁体，这部分没有问题。
- `fairy_1_00.dat` 里其余 8 个子文件与原版一致（这一项验证是有效的）。

## 二、数据库（46 个 `.dat`）—— 没发现会崩溃的问题

审查脚本：`workspace/audit_databases.py`

| 检查项 | 结果 |
| :--- | :--- |
| 记录数、记录区大小、字符串数 | 46/46 与原版一致 |
| 字符串指针以外的记录字节有没有被改 | 0 处被改 |
| 字符串字段位置和 PC 版布局对照（排查把数值误判成指针） | 能对照的 31 个文件里，不一致 0 处；其余 15 个文件因为 PC 版记录数不同没法对照（如 talk、item、string） |
| 控制标签 / `%s` 格式符前后一致 | 0 处不一致 |
| ID / 路径类字符串被改 | 只有预期内的 9 条贴图路由（`_TC` 改成 `_sc`），目标文件在 Switch 的 `texture_1_00.dat` 里都存在 |

低风险提示：
- `multiLineText.dat` 和 6 个 `player*.dat` 除了写入 TC 槽（slot 4），还把 **slot 6** 从空串填成了中文（共 242 处）。原版这些 TC 槽也是空的，说明游戏可能读的是别的槽，或者回落到日文。实机看起来没出问题，但建议之后只写确定会被读取的槽。
- `dat_tool.py` 识别字符串指针靠的是启发式匹配。没法和 PC 版对照的 15 个文件，理论上还有把数值误判成指针的可能，但之前实机测试正常。

上一轮之前已经在实机测过，本轮没动，不认为和这次报错有关。

## 四、建议处理顺序

1. **立刻**：从补丁目录里删掉（或改名移走）`output/.../romfs/data/fairy_1_00.dat`，其余文件保留，就能回到之前能正常运行的状态。建议先实机确认一遍，排除其他因素。
2. **修复路线 A（稳妥）**：先只替换 5 张原本就是 BC3 的贴图（标题 Logo、传单 101–104），同时修正 comp_sz（+20）和块高（取 ints[14] 的低字节），然后上机测试。
3. **修复路线 B（覆盖“开始/设定/售价/种子”等）**：需要先逆向出 `0x0B` 到底是什么格式（分析 `NmplDLL.nro` 的贴图创建代码，或用 ASTC 解码器去试）。然后二选一：
   - 用相同格式重新编码 PC 版的简中图；
   - 或者把这几张的描述符格式字节改成 `0x07`，按 BC3 写入。这条路需要验证引擎是否接受，同时要考虑内存变大。
4. 改造验证方式：以后都以 **Switch 原版贴图**为基准（解析出同样的字段，用原版规则解压），不再用自己写入的规则去验证自己。
